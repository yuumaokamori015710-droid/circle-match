# ログイン通知と認証頻度の検知

2026-11-02の本人指示で追加。既存の認証条件・ログイン可否・DB構造は変更しない。
Google/Supabaseの成功確認後、アプリ内通知を作成する。認証元が確認したメール宛先と
既存のResend設定がある場合だけ、既存の永続送信キューへ同じトランザクションで追加する。
未設定なら「アプリ内通知のみ」。送信サービス受付と受信箱への到着は区別する。

## 対象と重複防止

- Supabaseのトークンは従来どおり認証元のuserエンドポイントで確認する。
- サーバーで確認したユーザーID、ログイン方法、認証元のlast_sign_in_atで重複を防ぐ。
- 時刻がない場合は検証済みトークンからHMACを生成する。トークン本体は保存しない。
- Googleの既存ログイン可否は変更しない。email_verifiedでない宛先には新たな通知メールを送らない。
- ページ表示、api/me、既存Cookieの利用は新しいログイン通知の対象にしない。
- 任意の入力メールやuser_metadataのメール宛先に送信しない。
- 通知処理はSAVEPOINTで分離し、失敗した通知だけをロールバックする。既存セッションは維持する。

## 検知ルール

ルールベースのログイン周辺の行動分析であり、閲覧履歴の追跡や機械学習ではない。

- 同一アカウントの異なるログインを10分間に5件検知したら、本人へ確認通知。
- 同一アカウントの認証情報交換を10分の時間区分内に10回検知したら、本人へ確認通知。
- 認証失敗を同じサーバー観測接続元から10分の時間区分内に5回検知したら、運営の検知一覧へ記録。
- 確認通知はアカウントごと・10分区分ごとに1回。自動的なアカウント停止や不正判定はしない。
- 接続元は日別HMACのみ。X-Forwarded-For等の申告値は信用しない。プロキシ配下では複数利用者を含むため、個人・端末・所在地の特定とは扱わない。
- 上流認証サービスの通信障害や5xxは、認証失敗として数えない。

## 画面と保存

- /settings/security: 本人の通知・検知履歴と有効なアプリセッション件数。認証必須、no-store。
- /admin/security: 既存の管理者認証で保護した検知一覧。メール・IP・トークンは表示しない。
- 既存のapp_state、audit_logs、event_notifications、event_email_outboxだけを使う。新テーブル・本番マイグレーションはない。
- 匿名集計カウンターは1日、HMACの重複マーカーと検知監査は30日で削除。既存の他用途設定・監査・通知・送信記録は削除しない。
- 通知メールには日時とログイン方法、心当たりがない場合の窓口のみ。認証リンクやトークン、IPは含めない。

## 検証と運用

python -m unittest discover -s scripts -p "test_login_security.py"

一時DBと模擬認証・メールで検証する。preview_login_security.pyは8931番のループバックと
架空アカウントだけを使い、実送信しない。Cookieは他のローカルプレビューから分離する。
実際の受信は本番本人ログイン後に本人が確認する。検証前にStripeチェックリストを代理で選択・送信しない。
