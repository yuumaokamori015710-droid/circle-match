# Event Guest Admission

Member login and guest admission are separate paths. Anonymous visitors to an
open, offline-paid or free event can choose either. Stripe/online events still
require member login. Existing event IDs, tariffs, capacity rules and host fees
are unchanged. No schema or environment configuration changes are required.

Guests request an email link, verify it, review the existing individual/team
application form, accept the event conditions and explicitly submit. Merely
requesting/opening/verifying a link does not book a place. Guest applications use
the existing admission, approval, capacity, formation, bank transfer and
notification logic. Guest management includes attendance confirmation, private
host messages and cancellation; it does not grant access to member pages.

Anonymous `/events/<id>/apply` links go directly to the eligible event's guest
form. A member sign-in URL whose return destination is that application's form
also shows an explicit guest entry above the unchanged member login controls.
This prevents old/shared member links from trapping visitors at a login gate.
Hosting, account-management and online-only gates do not offer guest access.

The guest entry asks for the representative's name and email, not a Google or
member account. The bounded name is held with the 20-minute email proof and is
used only after verification to prefill that event's guest application. Existing
email-only proofs and guest sessions remain valid; no member session is created.

## Boundaries

- A 256-bit random, one-use proof is valid for 20 minutes for one event only.
- The proof is in a URL fragment; the isolated verification page clears it from
  the address bar, has no third-party content, prohibits framing and requires an
  explicit POST. GET does not redeem it. Tokens are hashed in private app state.
- A separate 7-day HttpOnly, SameSite=Lax, HTTPS-Secure cookie is path-scoped to
  that event. It never sets a member login cookie or creates a member session.
- Relational applicant records use an internal `event_guest` identity unique to
  verified email plus event. Those identities cannot authenticate as members.
- Mutations require same-origin JSON and an unexpired event-scoped capability.
- Canonical email duplication is checked transactionally across member and guest
  applications; active or unsettled applications cannot be duplicated.
- Existing guest applicants can request a fresh proof after the event closes,
  to recover access to announcements, payment status, cancellation and messages.
- Requests are limited to 1/minute and 4/hour per email, 40/15 minutes per
  observed peer, and 180/hour globally. Limiter identifiers are HMAC-hashed.
  Limits are not an assertion that forwarded proxy IPs identify unique people.
- Delivery failures are explicit, do not create applications and do not expose
  internal provider errors. Non-eligible addresses receive a neutral response.
- If the existing email provider is not configured, the guest CTA is omitted
  and member login remains usable. No live test messages or enrollments are
  generated by the test suite or the preview fixture.

## Verification

Run `python -B -m unittest discover -s scripts -p test_event_guests.py`, together
with existing event, formation, pricing, notification, payment and login tests.
`python -B scripts/preview_event_guests.py` creates a disposable loopback-only
fixture. Its `/qa/inbox` is a mocked inbox, never a production endpoint. End the
preview with Enter; temporary applicant records and proofs are removed.
